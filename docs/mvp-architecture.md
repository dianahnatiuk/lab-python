# MVP: лабораторний процес

## Процес і статуси
`registered` (рецепція) → `collected` (медсестра) → `in_lab` (лаборант приймає зразок)
→ `completed` (лаборант вносить результати). Перехід можливий лише на наступний крок
і лише для відповідної ролі; пропуск або повтор дає 409. Кожен перехід записується
в `order_status_history` (хто, коли, з якого статусу в який).

## Розподіл даних
- **PostgreSQL**: `users`, `patients`, `orders`, `order_status_history` — структуровані дані зі
  зв'язками та обмеженнями цілісності.
- **MongoDB**: колекція `results`, один документ на замовлення (`order_id` унікальний).
  Різні аналізи мають різний набір показників, тому гнучка JSON-схема доречна.
  Приклад: `{order_id, tests: [{code, name, value, unit, ref_min, ref_max, flag}], conclusion}`.

## Узгодженість між БД
Результати спочатку записуються в Mongo через upsert (ідемпотентно), потім у тій самій
операції оновлюється статус у PostgreSQL. Якщо PostgreSQL відмовить, повторне збереження
просто перезапише документ. Замовлення блокується `SELECT ... FOR UPDATE`, тому два
одночасні запити не виконають один перехід двічі.

## Доступ
- Пацієнт бачить лише свої замовлення, результати й PDF (інакше 403, захист від IDOR).
- Персонал бачить усі замовлення. Створює замовлення лише рецепція, забір відмічає
  медсестра, результати вносить лаборант.
- PDF доступний лише для статусу `completed`; формується на льоту з PostgreSQL + Mongo
  (reportlab, шрифт DejaVu для кирилиці).
