# Користувачі, ролі та розмежування доступу: архітектурні рішення

## Ролі
`patient`, `receptionist`, `nurse`, `lab_tech`, `admin` — відповідають етапам процесу
(реєстрація на рецепції → забір → лабораторія → результат). Роль зберігається
в `users.role` (рядок + Python Enum). Окрема таблиця ролей не потрібна, бо кожен
користувач має рівно одну роль, а набір ролей фіксований процесом.

## Реєстрація
Публічна реєстрація завжди створює `patient`; роль з тіла запиту ігнорується
(захист від підвищення привілеїв). Персонал створює лише адміністратор.

## Автентифікація
- Паролі: Argon2 (`argon2-cffi`), у БД лише хеш.
- Токен: JWT (HS256, 60 хв). Передається в httpOnly-cookie (браузерний UI,
  захист від крадіжки через XSS, SameSite=Lax проти CSRF) або в заголовку
  `Authorization: Bearer` (API, тести).
- Роль береться з БД на кожен запит, а не з токена, тому зміна ролі діє одразу.
- Однакова відповідь 401 для «немає користувача» і «хибний пароль», плюс
  вирівнювання часу перевірки (захист від перебору email).

## Контроль доступу
- Вертикальний: залежність `require_role(...)` повертає 403 для чужої ролі.
- Горизонтальний (IDOR): `PATCH /users/{id}` дозволений лише власнику чи адміну;
  оновлюється лише `full_name` (роль і email змінити не можна).
- Анонім: API → 401, HTML-сторінки → 302 на `/login`.

## Дані
PostgreSQL: користувачі, ролі, замовлення, статуси (цілісність, зв'язки).
MongoDB: JSON-результати аналізів (різний набір показників у різних аналізів).
